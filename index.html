What we mean by “UDF”

Any user‑defined code that runs as part of a Spark query.

The broad family

  • Scalar — one row in, one row out (the udf keyword)
  • Batched / per-partition — mapInPandas, mapPartitions
  • Grouped & aggregate — group map, UDAF
  • Table functions (UDTF) — one row in, many out
  • Streaming — foreachBatch, transformWithState

Why it matters

  • Built-ins can’t cover every domain
  • Calls into external libraries (ML, scientific)
  • Complex / domain logic that doesn’t map to operators
  • Unstructured & semi-structured data Spark doesn’t natively understand

Scope: inline Scala / Java (in-JVM) are out of scope. This talk: UDFs that run in a separate worker process — Python today, and new languages.

A client–server architecture. Logical plans on the wire. Forward‑compatible protocol.

Client

Spark server

  • Thin client — just send logical plans (defined in Protobuf)
  • Forward-compatible — upgrade the server, not the clients
  • Universal & language-neutral — reach Spark from any language

Logical plan: what your query does, before Spark runs it.  ·  gRPC + Protobuf: a standard, versioned way for programs to exchange messages.

UDFs are the one promise Spark Connect still can’t keep for most of them.

Spark Connect3 / 19
Problem 1
Multi-language

Languages are stuck without UDFs

Existing PySpark / Scala UDF machinery can’t be reused for new Spark Connect clients.

From the Apache Rust Spark Connect README

It’s not a Rust problem. It’s an architectural gap:

  • No standard protocol for sending a UDF to a worker and streaming data
  • No language-neutral worker contract Spark can talk to
  • Planning logic hard-wired to Python

The only UDFs that work today — inline JVM (Scala / Java) and PySpark — predate Connect and don’t generalize. Every new language re-invents the entire stack — or skips it.

Problem 1 · multi-language4 / 19
Problem 2
Forward compatibility

A UDF is more than a logical plan

Spark Connect works well for

  • Logical plans
  • Stable, version‑free semantics
  • Old clients running on newer servers

UDFs carry an environment

  • Language runtime — Java 17, Scala 2.13, Python 3.12…
  • Dependencies & versions
  • Serialized (pickled) function bodies — tied to a runtime version

Pickling = turning your function into bytes to ship it. Server upgrades → old UDFs may quietly break.

The hard part

Each language defines its own worker that executes the UDF — pulling in a whole execution environment. So a newer engine has to handle UDFs from older client versions — and even several client versions at once.
The logical plan stays compatible — the UDF’s runtime doesn’t come for free.

Problem 2 · forward compatibility5 / 19
Problem 3
Resources

UDFs are caged inside the Spark cluster

UDF execution is tied to executor-local resources today. Even when the user code runs in a side worker process, it shares the executor’s node, scheduling model, and cluster hardware.

  • Lightweight UDFs — fine
  • Heavy UDFs — OOMs, contention, evictions
  • Mismatched hardware — need a GPU the cluster doesn’t have

What that forces today

  • Over-size the whole cluster for one UDF
  • Or it just can’t run in Spark

The resource model is a constraint, not a choice.

Credit where it’s due

PySpark already runs UDFs brilliantly

Powerful, efficient, and battle‑tested in production for years.

Spark executor
runs your tasks
socket
↔
Python worker
where your code runs

Your Python code doesn’t run inside Spark — it runs in a separate worker process next to each executor.

Already covers a wide surface: scalar, pandas-batched, grouped map, table functions, aggregators.

The shape

  • Separate process — a worker runs alongside each executor
  • Data — Arrow (fast, language-neutral data layout), or pickle for some types
  • Planning — Python-specific rules baked into the engine
PySpark today7 / 19
The catch

… but it doesn’t generalize to other languages

Planning is mature — but Python‑tied

  • Plans UDFs to run outside the JVM
  • Mature chaining + query optimization
  • But closely tied to Python — nothing for Go / Rust / Swift to reuse

Hand-written socket protocol

# worker.py
read_int(infile)
read_long(infile)
read_bytes(infile)
# position-oriented, brittle
  • Position-oriented & brittle
  • Hard to version, evolve, or reuse

Worker coupled to the engine

  • Launch & management wired into the core
  • Provisioning can’t be reused by other languages
  • Worker ships with the engine — old client can hit a newer worker (forward-compat problem)
PySpark limitations8 / 19
The approach

Three pillars

Language‑agnostic where it can be. Language‑specific only where it must be.

Each pillar makes one thing replaceable without touching the others.

Architecture overview9 / 19
Pillar 1
Language-agnostic planning

Plan by shape, not by language

  • Scalar — one row in, one row out
  • mapPartitions — a whole partition at a time
  • Grouped map — input grouped by key
  • Table function — one row in, many out
  • Aggregator — multi-round reduce/merge

These shapes are what Spark needs to plan the work — none of it is Python-specific.

The shape decides the plan

  • How to partition the data
  • Which physical operator to use
  • How results are gathered back

All of it from the shape — none of it from the language.

Pillar 1 · planning10 / 19
Pillar 2
Execution protocol

One protocol — Init → Data → Finish, over any transport

Every UDF execution, any type, runs the same three phases:

  • Init — connect; send the UDF body + schemas
  • Data — stream input in, results back (independent directions)
  • Finish — flush, release, terminate

Over any transport

Today: a raw socket — implicit & position-based, contract hidden in worker.py — version-fragile.
New: Protobuf + gRPC — explicit, reusable across languages.

Protobuf: schema + versioning (schema evolution). gRPC: streaming, back-pressure, failure recovery, debuggability, language-neutral.

Pillar 2 · protocol11 / 19
Pillar 3
Worker spec

The worker specification — a declarative contract

Spark orchestrates. Languages bring their own runtime.

What the spec declares

  • Start — launch script / callable
  • Connect — UDS · TCP · gRPC endpoint
  • Clean up — verify · install · terminate
  • Capabilities — data format · parallelism · chaining

What changes for Spark

  • No language specifics in the engine
  • Runtimes & deps live in the worker (local · container · remote)
  • Client owns the spec — old client, newer server still works
  • Spark plans, schedules & pools off its capabilities
Pillar 3 · worker spec12 / 19
Pillar 3
Beyond local

Same contract — local, container, or remote

Local process

Spawn next to executor

  • Pre-installed runtime
  • Launch script + UDS endpoint
  • SIGTERM/SIGKILL lifecycle

Today’s PySpark fits here.

Container

Docker / OCI image

  • Pre-install Docker + image
  • Launcher starts a container
  • Stronger isolation, hermetic deps
Remote (future)

Worker outside the cluster

  • Dedicated / GPU compute, or a service like AWS Lambda
  • Indirect provisioning — spec returns an endpoint
  • Same protocol on the wire

The protocol is the boundary — but Spark still controls the workers through the spec: reuse, parallelism-aware scheduling, and pools by security scope.

Putting it together
End to end

Adding a UDF in a new language — end to end

What the language author does · what Spark does — the three pillars in action.

You — the language author
  • 1 · Implement a gRPC worker for the protocol (P2)
  • 2 · Describe provisioning in a worker spec (P3)
  • 3 · Send the spec + the query’s logical plan
Spark
  • Plans by shape — any language (P1)
  • Provisions & orchestrates workers per the spec (P3)
  • Forwards requests & exchanges data (P2)

One gRPC worker + one spec per language — Spark does the rest, the same way every time.

How it works · end to end14 / 19
JVM UDFs
Existing language

What about JVM UDFs?

Inline stays in-process. Isolation becomes an option.

Unchanged

Inline Scala / Java UDFs

  • Run in the executor JVM, in-process
  • No cross-process hop, no serialization — the fastest path
  • Out of scope — we don’t touch them
Where the protocol shines

JVM UDFs that need isolation

  • Isolated classpath — no conflicts with Spark’s
  • Conflicting or heavy dependencies
  • A different JVM version or tuning

Run it as a separate worker — same contract, on demand.

JVM UDFs15 / 19
PySpark UDFs
Existing language

Don’t replace the PySpark worker — split the seam

The goal: unify all UDF paths, including PySpark — but only after full validation. Rule #1: don’t change existing behavior — so separate transport from UDF logic.

The trap

A whole new gRPC worker

  • Two parallel UDF implementations
  • Double the bugs; the paths drift
  • Risks the huge existing install base

Instead: one processing core, swappable transport underneath.

UDF processing logic  (deserialize · run · serialize)
shared — unchanged across transports
↔
Transport adapter
the new seam — chooses the channel
Socket transport
socket / Python path stays default until full validation
gRPC transport
new · opt-in · structured

Shipping now in apache/spark · udf/worker — transport-agnostic core, gRPC over a Unix-domain socket (local, fast) as the first transport.

BACKUP · Pillar 2
Illustrative

Illustrative protocol

service UdfWorker {
  // one execution = one bidi stream
  rpc Execute(stream UdfRequest)
      returns (stream UdfResponse);

  rpc Manage(WorkerRequest)
      returns WorkerResponse;
}

message UdfRequest {
  oneof request {
    UdfControlRequest control = 1;
    DataRequest       data    = 2;
  }
}

message UdfControlRequest {
  oneof control {
    Init   init   = 1;
    Finish finish = 2;
    Cancel cancel = 3;
  }
}
message DataBatch {
  bytes  raw    = 1;
  Format format = 2;
}

enum Format {
  FORMAT_UNSPECIFIED = 0;
  FORMAT_ARROW       = 1;
  FORMAT_AVRO        = 2;
}

message DataRequest {
  DataBatch data = 1;
  map<string,string> metadata = 2;
  // batch id, grouping key, ...
}

// Spark streams input → worker.
// Worker streams results → Spark.
// Control + data are independent.
