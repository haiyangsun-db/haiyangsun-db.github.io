What we mean by “UDF”

Any user‑defined code that runs as part of a Spark query.

The broad family

  • Scalar — one row in, one row out (the udf keyword)
  • Batched / per-partition — mapInPandas, mapPartitions
  • Grouped & aggregate — group map, UDAF
  • Table functions (UDTF) — one row in, many out
  • Streaming — foreachBatch, transformWithState

Why it matters

  • Built-ins can’t cover every domain
  • Calls into external libraries (ML, scientific)
  • Complex / domain logic that doesn’t map to operators
  • Unstructured & semi-structured data Spark doesn’t natively understand

A client–server architecture. Logical plans on the wire. Forward‑compatible protocol.

Client

Forward compatibility: upgrade the server, leave clients untouched.
That keeps Spark applications stable and maintainable over time.

Problem 1
Multi-language

Languages are stuck without UDFs

Existing PySpark / Scala UDF machinery can’t be reused for new Spark Connect clients.

From the Apache Rust Spark Connect README

// supported:
DataFrame · SQL · Reads/Writes · Group-by ✓

// blocked:
UDF       not possible
UDTF     not possible

It’s not a Rust problem. It’s an architectural gap:

  • No standard protocol for sending a UDF to a worker and streaming data
  • No language-neutral worker contract Spark can talk to
  • Planning logic hard-wired to Python

Every new language ends up having to re-invent the entire UDF stack — or just skip it.

Problem 1 · multi-language4 / 18
Problem 2
Forward compatibility

UDFs don’t fit cleanly in a client–server world

Spark Connect works well for

  • Logical plans
  • Stable, version‑free semantics
  • Old clients running on newer servers

UDFs carry an environment

  • Language runtime — Java 17, Scala 2.13, Python 3.12…
  • Dependencies & versions
  • Serialized (pickled) function bodies — tied to a runtime version

Pickling = turning your function into bytes to ship it. Server upgrades → old UDFs may quietly break.

Concrete example

An older client defines a UDF — its serialized body assumes specific Python & library versions. Run it on a newer server whose bundled runtime has moved on, and the function can break.
The logical plan stayed compatible — the UDF’s runtime didn’t.

Problem 2 · forward compatibility5 / 18
Problem 3
Resources

UDFs are caged inside the Spark cluster

UDF execution is tied to executor-local resources today. Even when the user code runs in a side worker process, it shares the executor’s node, scheduling model, and cluster hardware.

  • Lightweight UDFs — fine
  • Heavy UDFs — OOMs, contention, evictions
  • Mismatched hardware — need a GPU the cluster doesn’t have

What that forces today

  • Over-size the whole cluster for one heavy UDF
  • Or pull the data out and run the model elsewhere by hand
  • Or skip it — the workload just can’t run in Spark

The resource model is a constraint, not a choice.

… and why it can’t scale as‑is

Planning is Python‑specific

The engine’s UDF planning rules only understand Python — nothing for Go / Rust / Swift to reuse.

Hand-written socket protocol

# worker.py
read_int(infile)
read_long(infile)
read_bytes(infile)
# position-oriented, brittle

Hard to version, hard to evolve, hard to reuse.

Engine coupled to language specifics

Launching and managing the language worker is wired into the core. The engine should be decoupled from any one language’s details.

Proposal

Three pillars

Language‑agnostic where it can be. Language‑specific only where it must be.

01 Pillar 1

Language‑agnostic planning

Plan UDFs by their execution shape, not by language. Standardized data formats (Arrow first).

02 Pillar 2

Standardized execution protocol

One structured, versioned, streaming protocol between Spark and any worker. init → data → finish.

03 Pillar 3

Declarative worker specification

The client tells Spark how to start, connect, expect — runtimes leave the engine.

Each pillar makes one thing replaceable without touching the others.

Architecture overview9 / 18
Pillar 1
Language-agnostic planning

Plan by shape, not by language

  • Scalar — one row in, one row out
  • mapPartitions — a whole partition at a time
  • Grouped map — input grouped by key
  • Table function — one row in, many out
  • Aggregator — multi-round reduce/merge

These shapes are what Spark needs to plan the work — none of it is Python-specific.

The shape decides the plan

  • How to partition the data
  • Which physical operator to use
  • How results are gathered back

All of it from the shape — none of it from the language.

Pillar 1 · planning10 / 18
Pillar 2
Execution protocol

One protocol — Init → Data → Finish, over any transport

Every UDF execution, any type, runs the same three phases:

  • Init — connect; send the UDF body + schemas
  • Data — stream input in, results back (independent directions)
  • Finish — flush, release, terminate

Over any transport

Today: a raw socket — contract hidden in worker.py.
Proposal: a structured one — gRPC + Protobuf — added alongside. Same lifecycle on both.

  • Schema evolution — add fields without breaking
  • Streaming + back-pressure (receiver can slow the sender)
  • Every language already has the tooling

Pillar 2
Adoption without disruption

Don’t replace the PySpark worker — split the seam

Rule #1 for PySpark: don’t change existing behavior. So separate transport from UDF logic, and make transport pluggable.

The trap

A whole new gRPC worker

  • Two parallel UDF implementations
  • Double the bugs; the paths drift
  • Risks the huge existing install base

Instead: one processing core, swappable transport underneath.

UDF processing logic  (deserialize · run · serialize)
shared — unchanged across transports
↔
Transport adapter
the new seam — chooses the channel
Socket transport
socket / Python path stays default until full validation
gRPC transport
new · opt-in · structured

Shipping now in apache/spark · udf/worker — transport-agnostic core, gRPC over a Unix-domain socket (local, fast) as the first transport.

Pillar 2 · adapter layer12 / 18
Pillar 3
Worker spec

The worker specification — a declarative contract

Spark orchestrates. Languages bring their own runtime.

What the spec declares

  • How to start the worker — a callable / launch script
  • How Spark connects — UDS path, TCP port, gRPC endpoint
  • How to clean up — verify, install, terminate
  • What to expect — data formats, parallelism, reuse, chaining

What changes for Spark

  • No language specifics baked into the engine
  • Runtimes & deps live in the worker environment — local install, container image, or remote service — the spec describes how Spark reaches it
  • Engine decoupled from language details — the client owns the spec, on its own version track, so an old client keeps working on a newer server (part of what restores forward compatibility)
  • Spark routes planning & scheduling off the spec’s capabilities
  • Pool workers by spec hash + security scope — safely reuse them

Pillar 3
Beyond local

Same contract — local, container, or remote

Local process

Spawn next to executor

  • Pre-installed runtime
  • Launch script + UDS endpoint
  • SIGTERM/SIGKILL lifecycle

Today’s PySpark fits here.

Container

Docker / OCI image

  • Pre-install Docker + image
  • Launcher starts a container
  • Stronger isolation, hermetic deps
Remote (future)

Worker outside the cluster

  • Dedicated / GPU compute, or a service like AWS Lambda
  • Indirect provisioning — spec returns an endpoint
  • Same protocol on the wire

The protocol is the boundary. Where the worker lives stops being Spark’s concern.

Why it matters

What this unlocks

Any language — not just Python

Problem 1. New communities implement UDFs once against a shared protocol — Go, Rust, Swift, .NET stop re-inventing the stack.

UDF runtimes decoupled from Spark upgrades

Problem 2. The runtime versions on its own track, not the engine’s — fewer UDF surprises across upgrades.

Run heavy & GPU UDFs anywhere

Problem 3. Container, remote, or GPU workers — resources become a choice, not a constraint.

And Spark itself gets lighter — new execution shapes arrive as specs, not engine rewrites.

If you write PySpark today: nothing breaks — your existing UDFs keep working, most of this is under the hood, and new options (GPU, remote) are opt-in.

BACKUP · Pillar 2
Illustrative

Illustrative protocol

service UdfWorker {
  // one execution = one bidi stream
  rpc Execute(stream UdfRequest)
      returns (stream UdfResponse);

  rpc Manage(WorkerRequest)
      returns WorkerResponse;
}

message UdfRequest {
  oneof request {
    UdfControlRequest control = 1;
    DataRequest       data    = 2;
  }
}

message UdfControlRequest {
  oneof control {
    Init   init   = 1;
    Finish finish = 2;
    Cancel cancel = 3;
  }
}
message DataBatch {
  bytes  raw    = 1;
  Format format = 2;
}

enum Format {
  FORMAT_UNSPECIFIED = 0;
  FORMAT_ARROW       = 1;
  FORMAT_AVRO        = 2;
}

message DataRequest {
  DataBatch data = 1;
  map<string,string> metadata = 2;
  // batch id, grouping key, ...
}

// Spark streams input → worker.
// Worker streams results → Spark.
// Control + data are independent.
